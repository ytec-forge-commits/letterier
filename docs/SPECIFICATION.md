# 0. この改訂版の位置づけ

本書は、旧仕様書をベースに、開発着手前の再検討と1問1答による仕様確認を反映した改訂版である。

旧仕様書の基本思想である、

> 「便箋を作るための簡易DTPソフト」

は維持する。

ただし、今回の再検討により、単に文字オブジェクトを自由配置するDTP型アプリではなく、

> **「便箋の上へ直接文章を書き、本文は自動で流れ、必要な写真・装飾・署名などを自由に配置できる、手紙作成特化アプリ」**

として設計を明確化する。

本アプリでは、自由度だけを追求しない。

特にシニア層を含む一般ユーザーが、

1. テンプレートを選ぶ
2. 便箋の上へそのまま文章を書く
3. 必要なら写真や装飾を置く
4. 印刷またはPDF保存する

という流れで使えることを最優先する。

# 1. プロジェクト概要

## 1.1 名称

正式名称:

**レタリエ**

Letter + Atelier。「一通の手紙をつくる、小さなアトリエ」。
説明用表記: レタリエ — 手紙・便箋作成アプリ。
旧開発名: 便箋工房。

本仕様書では正式名称「レタリエ」を使用する。名称変更により機能・デザイン・保存形式の仕様は変更しない。

## 1.2 目的

Microsoft Wordや一般的なDTPソフトでは、手紙を作成する際に、

- 罫線
- 文字位置
- 行間
- 縦書き
- 画像
- ページ設定
- 印刷余白

などの調整が煩雑になりやすい。

レタリエでは、これらを手紙・便箋用途に最適化し、

> **「文章を書くことに集中できるWindowsアプリ」**

を実現する。

## 1.3 主用途

本アプリの主用途は、

**印刷した便箋へ手書きするための用紙作成ではなく、本文もアプリ内で入力し、完成した手紙を印刷・PDF保存すること**

とする。

手書き用便箋としての利用を禁止するものではないが、UI・文章フロー・保存・テンプレートは「本文をアプリ内で作成する」用途を中心に設計する。

# 2. 対象ユーザーとUX方針

## 2.1 主な対象

- Windowsを日常的に利用している一般ユーザー
- Wordの詳細なレイアウト操作が難しいと感じるユーザー
- 手紙・お礼状・季節の便りを作成したいユーザー
- シニア層
- PC初心者〜中級者

## 2.2 UX原則

以下を最優先する。

1. 専門用語を極力使わない
2. 操作結果を画面上ですぐ確認できる
3. 保存操作を意識しなくても文章を失いにくい
4. 自動調整は行うが、ユーザーの意図を勝手に変更しない
5. 印刷前に問題を発見できる
6. 縦書きでも横書きでも操作方法を極端に変えない
7. ボタン・文字・選択状態を見やすくする
8. 小さすぎるクリック領域を避ける
9. 重要な操作は取り消せる
10. 「手紙を書く」目的に不要なDTP機能を前面に出さない

# 4. アプリ形態・技術方針

## 4.1 形態

Webアプリではなく、**Windowsデスクトップアプリ**として開発する。

配布形式は、

- Windowsインストーラー
- 必要に応じて単体実行可能形式

を想定する。

## 4.2 推奨技術スタック

第一候補:

- Tauri
- React
- TypeScript

ただし、編集エンジンは旧仕様の「Canvas / SVG」に固定しない。

今回の仕様では、

- 本文の直接入力
- キャレット表示
- 部分書式
- 縦書き
- 禁則処理
- 自動改ページ
- 画像回り込み
- 高品質PDF/印刷

が重要であるため、実装開始前に小規模な技術検証を行う。

## 4.3 編集エンジンの推奨方向

以下の役割分担を優先検討する。

### DOM / HTML / CSS

主に:

- 本文
- 直接入力
- キャレット
- 選択範囲
- 部分書式
- 横書き
- 縦書き
- 文字レイアウト

### SVG / Canvas

主に:

- 罫線
- ガイド
- 選択枠
- 装飾
- 印刷安全領域
- 必要なオーバーレイ

最終採用方式は、後述する「技術検証ゲート」を通過した方式とする。

# 5. 最重要アーキテクチャ原則

今回の改訂で最も重要な点である。

## 5.1 本文と自由配置テキストを分離する

旧仕様の「すべての文字を独立TextObjectとして自由配置する」方式を、本文の中心モデルにはしない。

文字は最低でも次の2種類に分ける。

### BodyFlow

手紙本文。

特徴:

- 便箋上へ直接入力
- 罫線に沿って自動配置
- ページ末尾で自動改ページ
- 複数ページを連続して流れる
- 画像を回り込む
- 部分書式対応
- 横書き/縦書き対応

### FloatingTextObject

自由配置文字。

用途例:

- 宛名
- 日付
- 署名
- キャプション
- 補足
- 見出し

特徴:

- 好きな位置へ配置
- 本文とは独立した書式
- 必要に応じて本文へ追従、またはページ固定

## 5.2 UIと文書レイアウトを分離する

以下を分離する。

- UI状態
- 文書データ
- レイアウト計算
- 罫線生成
- PDFレンダリング
- 印刷レンダリング
- 保存
- 履歴
- テンプレート
- アプリ外観テーマ

## 5.3 画面表示と出力の共通化

編集画面、PDF、印刷でレイアウト結果が大きく異ならないよう、

**同一の文書レイアウトモデルから表示・出力を生成する**

ことを原則とする。

# 6. 文書全体の設定

今回の改訂では、以下は文書全体で統一する。

- 用紙サイズ

## 6.1 用紙サイズ

### A4

### B5

182 × 257 mm

### はがき

100 × 148 mm

## 6.2 用紙方向

- 縦
- 横

## 6.3 書字方向

### 横書き

- 左 → 右
- 横罫線

### 縦書き

- 右 → 左
- 縦罫線

文書作成後の書字方向変更は可能としてよいが、既存内容への影響をプレビューし、破壊的変更を勝手に確定しないこと。

# 8. 罫線

レタリエの中心機能。

## 8.1 種類

- 横罫線
- 縦罫線
- 罫線なし

## 8.2 設定項目

- 線間隔
- 線幅
- 線色
- 開始位置
- 終了位置
- 上下左右余白
- 表示範囲

線間隔はmm単位で設定可能とする。

例:

- 6 mm
- 7 mm
- 8 mm
- 9 mm
- 10 mm

## 8.3 罫線生成

罫線は画像として保持しない。

設定値から自動生成する。

例:

`8 mm → 9 mm`

へ変更した場合、罫線全体を再計算する。

## 8.4 罫線の均一性

ページ内の罫線は、原則として等間隔を維持する。

本文中の一部文字を大きくし、その文字が罫線間隔に収まらなくなる場合、

**その行だけ罫線間隔を広げてはならない。**

ユーザーへ次を案内する。

- 文字サイズを小さくする
- そのページ全体の罫線間隔を広げる

勝手に文字を縮小しない。

勝手に一部罫線だけ移動しない。

縦書きの場合は同じ考え方を列間隔へ適用する。

# 9. 本文入力

## 9.1 入力方式

本文は、別の文章入力欄ではなく、

**便箋の上へ直接入力する。**

ユーザーは完成形を見ながら文章を書く。

## 9.2 本文フロー

本文は連続したBodyFlowとして保持する。

以下を自動化する。

- 罫線に沿った配置
- 改行
- 自動改ページ
- 画像回り込み
- 縦書き時の列送り

## 9.3 部分書式

本文全体の基本書式を持つ。

そのうえで、選択した一部分だけ変更可能とする。

最低限:

- フォント
- フォントサイズ
- 太字
- 斜体
- 下線
- 文字色

必要に応じて:

- 透明度
- 文字間隔
- 行間
- 揃え

を追加してよい。

---

# 10. 縦書き

初回実用版の必須機能。

「横書き完成後の将来機能」にはしない。

## 10.1 必須考慮

- 日本語文字の縦配置
- 句読点
- 括弧
- 長音
- 小書き文字
- 禁則処理
- 縦中横
- フォント差による表示差

## 10.2 縦中横

基本動作:

- 独立した2桁数字は自動で縦中横を適用
- 例: `12月` の `12`

ただし、

`2026`

のような長い数字を、

`20` + `26`

へ勝手に分割して縦中横にしない。

## 10.3 個別変更

自動縦中横を基本としつつ、

ユーザーが選択した箇所について、

- 縦中横にする
- 通常の縦配置へ戻す

を切り替えられる。

---

# 11. 自動改ページ

本文がページ末尾へ到達した場合、自動で次ページへ続く。

## 11.1 続きページのデザイン

自動生成されるページでは、

**「続きのページ用デザイン」**

を使用する。

テンプレートは最低でも、

- 1ページ目用
- 2ページ目以降用

の2種類のデザイン定義を持つ。

例:

1ページ目:
華やかな桜

2ページ目以降:
同系統だが装飾を抑えた桜

途中のページだけ背景や罫線を個別変更しても、その変更を後続ページへ自動波及させない。

## 11.2 段落の孤立行処理

文書設定として、次をユーザーが選択できる。

### OFF

ページへ入るところまで詰める。

段落の最後の1行だけ次ページへ移っても調整しない。

### ON

段落の先頭または末尾の1行だけが別ページに取り残される場合、改ページ位置を調整する。

例:

`4行 + 1行`

ではなく、

`3行 + 2行`

となるよう調整する。

文字サイズや罫線間隔は変更しない。

推奨初期値:

**ON**

# 12. 手動改ページ

自動改ページに加え、

本文中の任意位置へ、

**「ここから次のページ」**

を指定できる。

## 12.1 手動改ページの特徴

- 前方の文章を増減しても維持する
- 編集画面だけに目印を表示する
- PDFには表示しない
- 印刷には表示しない
- ユーザーが削除できる
- 段落孤立行の自動調整より優先する

# 14. 画像と本文の回り込み

写真・イラストを配置した場合、

**本文は画像の周囲を自動で避ける。**

初期版では、

- 画像の四角い外枠
- 指定した余白

を回り込み領域として使用する。

人物や花の輪郭そのものを解析して回り込む機能は初期必須としない。

背景画像は回り込み対象外。

---

# 15. 画像と罫線の関係

画像ごとに、次の2種類を切り替えられる。

## 15.1 罫線をそのまま表示

画像の背面にも罫線を描画する。

透明画像では透明部分から罫線が見える。

## 15.2 画像の周囲だけ罫線を隠す

本文が回り込む領域と同様に、

- 画像外枠
- 余白

の範囲だけ罫線を描画しない。

画像を移動・削除した場合、罫線は元へ戻る。

## 15.3 注意

この設定で変わるのは罫線描画だけ。

本文の画像回り込みは別設定として維持する。

推奨初期値:

**画像の周囲だけ罫線を隠す**

---

# 16. オブジェクトの追従と固定

写真、画像、FloatingTextObject等は、要素ごとに次を選択できる。

## 16.1 本文へ追従

関連する本文位置に追従する。

用途例:

- 写真
- 写真キャプション
- 署名
- 関連イラスト

## 16.2 ページ上の位置へ固定

本文の増減とは無関係に、そのページ上の位置へ固定する。

用途例:

- 飾り
- コーナーイラスト
- ページ固有装飾

初期操作では追従を基本にし、必要な場合のみ固定へ変更できるUIを推奨する。

---

# 17. 背景

背景は通常オブジェクトから分離する。

設定:

- 背景なし
- 単色
- 画像

画像の場合:

- 表示位置
- サイズ
- 拡大縮小
- トリミング
- 透明度

背景は通常編集で誤選択しない。

「背景を編集」などの明示操作でのみ選択できるようにする。

1. 背景

3. 画像

# 19. 複数ページ

1つの文書内で複数ページを管理する。

## 19.1 ページ一覧

画面下部などに、

`[ 1 ] [ 2 ] [ 3 ] [ + ]`

のようなページ一覧を表示する。

## 19.2 ページ操作

- 追加
- 削除
- 複製
- 並び替え

を可能とする。

## 19.3 本文フローとページ操作の関係

本文は連続フローであるため、ページ複製・並び替えは慎重に扱う。

ページ操作時点で、

- そのページに存在する本文範囲
- その本文へ追従する画像
- そのページ固定の画像
- 装飾
- FloatingTextObject

を対象として確認画面へ表示する。

ユーザーが確定した後、まとめて複製・移動する。

### 重要

ページを「画像として固定」してはならない。

移動・複製後も本文は編集可能であり、文章を追加すれば複数ページへ広がってよい。

段落がページ境界で分割されている場合、対象範囲を明示し、ユーザーが内容を確認してから確定する。

ページ移動・複製操作全体をUndo可能とする。

# 33. 保存履歴

自動保存と履歴作成は分離する。

## 33.1 通常履歴

**直近50世代**

を標準保持する。

設定で100世代などへ増やせる設計にしてよい。

## 33.2 履歴作成タイミング

変更がある場合に、

- 日時

を確認して復元できる。

つまり、

**「過去へ戻したあと、戻す前の状態へ再び戻れる」**

こと。

通常の`.binsen`と明確に区別すること。

人へ渡す通常の便箋ファイルに、過去の書き直し内容を含めない。

# 44. データモデル案

これは実装開始時のたたき台であり、最終型を強制しない。

ただし、

**BodyFlow と FloatingObject を分ける思想は維持すること。**

```ts
interface Project {
  version: number;
  name: string;
  documentSettings: DocumentSettings;
  body: BodyFlow;
  pages: PageState[];
  floatingObjects: FloatingObject[];
  templateInfo?: TemplateInfo;
}

interface DocumentSettings {
  paperType: "A4" | "B5" | "POSTCARD";
  orientation: "portrait" | "landscape";
  writingMode: "horizontal" | "vertical";
  orphanControl: boolean;
}

interface BodyFlow {
  blocks: FlowBlock[];
}

type FlowBlock =
  | ParagraphBlock
  | ManualPageBreakBlock;

interface ParagraphBlock {
  id: string;
  runs: TextRun[];
}

interface TextRun {
  text: string;
  style: TextStyle;
  verticalInlineMode?: "auto" | "normal" | "tate-chu-yoko";
}

interface PageState {
  id: string;
  ruling: RulingSettings;
  background: BackgroundSettings;
  overrides?: PageVisualOverrides;
}

type FloatingObject =
  | ImageObject
  | FloatingTextObject;

interface ImageObject {
  id: string;
  assetId: string;
  anchorMode: "flow" | "page";
  anchorTarget?: string;
  pageId?: string;
  position: PositionMm;
  size: SizeMm;
  wrap: ImageWrapSettings;
  rulingBehavior: "show-through" | "hide-around";
}

interface FloatingTextObject {
  id: string;
  anchorMode: "flow" | "page";
  anchorTarget?: string;
  pageId?: string;
  position: PositionMm;
  content: RichTextContent;
}

interface RulingSettings {
  enabled: boolean;
  direction: "horizontal" | "vertical";
  spacingMm: number;
  lineWidthMm: number;
  color: string;
  marginMm: {
    top: number;
    right: number;
    bottom: number;
    left: number;
  };
}
```

1. 一度に大規模変更を行わない
2. フェーズ単位で実装する
3. 各フェーズでビルド確認
4. 各フェーズで起動確認
5. 既存機能を壊さない
6. 変更理由を記録
7. TODOは具体的に記録
8. 仮実装は明記
9. テスト可能な構造を維持
10. UIコードへファイルI/Oを直接混在させない
11. PDF/印刷をUIから分離
12. レイアウト計算をUIから分離
13. 保存履歴を文書本体から分離
14. アプリ外観テーマを文書データから分離
15. 技術上の懸念を隠して実装を進めない

# 52. 完成イメージ

最終的には、

```text
Wordを開く
↓
罫線を作る
↓
行間を調整する
↓
文字枠を作る
↓
ページを調整する
↓
写真を置く
↓
印刷位置を直す
```

という作業を、

```text
レタリエを開く
↓
好きな便箋を選ぶ
↓
便箋の上へ文章を書く
↓
必要なら写真を置く
↓
印刷 / PDF
```

まで簡略化する。

# 53. 開発ゴール

ユーザーが、

> 「手紙を書きたい」

と思ったときに、

Wordや一般的なDTPソフトより先に、

**レタリエを起動したくなること。**

高機能であることより、

- 分かりやすい
- 壊れにくい
- 文章を失いにくい
- 仕上がりを想像しやすい
- 縦書きでも使いやすい
- 印刷で失敗しにくい

ことを優先する。

特に、

**「アプリの操作を覚える」のではなく、「手紙を書く」ことに集中できること**

を完成基準とする。
